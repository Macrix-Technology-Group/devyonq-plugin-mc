01What you are installing

Mission Control is a way of running software projects where people and AI agents work together. A Mission is one project. It writes down three things up front: what it will deliver, who is accountable, and how you will know it is done.

The unusual part is that a Mission has to prove what it says about itself. Every number in it can be re-checked later by someone who was not in the room.

Version 1.6 was just text files. You gave someone the instructions and they followed them. Version 1.7 also ships code. That is the big change, and it happened for one reason. It is worth two minutes, because everything else in this guide follows from it.

The bug that made us write a program

Every Mission that uses agent fleets has to write down a fingerprint of the code those fleets run. It is a checksum, like a file hash. If the code changes, the fingerprint changes.

How to work out that fingerprint was written down as instructions, in a document. Someone turned those instructions into a shell command. The command had a bug. It deleted comment lines starting with #, which is how shell scripts write comments. But the file was JavaScript, where comments start with //. So it deleted nothing, and 325 lines stayed in that should have come out.

Now the part that matters. The Mission used that command to work out its fingerprint. The checker used the same command to check it. Both got the same wrong answer, so they matched, and the check passed.

Nobody would ever have caught it. The code itself would not have recognised the number written in its own Mission file.

The lesson: if a check uses its own copy of a rule, and that copy is wrong, the check agrees with itself and proves nothing.

So in v1.7, anything a computer can work out lives in a program, the harness, and the document points at it. And when something needs that fingerprint, it asks the code to work it out.

So three things work together. You install the first two; the third runs in DevyonQ.

  • Skills are step-by-step instructions an AI agent follows. They hold the parts that need judgement: asking you questions, weighing an answer, deciding whether something is good enough.
  • The client mc17 is a small program that ships beside the skills, in client/. Every skill and every hook calls it. You sign it in to DevyonQ once per computer, with mc17 login, and it sends each command to the harness of your DevyonQ tenant.
  • The harness is code that runs in DevyonQ. It does the parts a computer can do exactly: work out checksums, check that required fields are filled, fill in templates, read and write the Mission's documents in CanonQ. When something is wrong it says no and tells you which line.

02The shape of the system

Five layers. The law is text you pin. The skills are procedures an agent runs. The program computes. The runner guards fleet execution. The store holds everything a Mission produces.

The one idea to keep

When you need to check a number, ask the code that produced it. Never follow a written-down copy of how it works. That is the whole idea. Everything above is built to make it true.

03Install

Two commands inside Claude Code, three runtimes, and a sign-in. The plugin of the old repository, Macrix-Technology-Group/devyonq, stays installable beside this one; switch one of the two on at a time.

Check the runtimes first

The plugin needs Node for the client mc17, Python 3 for the gate hooks, and git.

terminal
node --version   # v22 or newer
python3 --version
git --version

Add the marketplace and install

Run these inside Claude Code. The marketplace is a GitHub repository; the plugin is one entry in it.

claude code
/plugin marketplace add Macrix-Technology-Group/devyonq-mc
/plugin install devyonq-mc@devyonq-mc

Confirm it landed. The skills announce themselves when you ask for their parameters, which runs nothing:

claude code
/mc-cre-mission-v17 ?

Check the client runs

The plugin ships the client beside its skills. This asks it which plugin and which copy of the harness contract it carries, and which DevyonQ it is signed in to. It answers on its own and sends nothing:

terminal · from the installed plugin directory
client/mc17 version

Plugin   : devyonq-mc <version>
Contract : version 1, sha256:…, copied from devyonq-saas …
Gateway  : none; run mc17 login in a terminal of your own
Tenant   : none

On Windows, from PowerShell or cmd, run client\mc17.cmd in place of client/mc17, here and in every command of this guide.

Why the tests matter more than their count

The plugin's own suites run in its repository, and every check in them was deliberately broken first, to watch it go red, then restored to watch it go green. That sounds like overkill until you know that this project once shipped a checker that could not fail at all: it printed problems and then reported success, every single time, for weeks. A check you have never seen fail tells you nothing.

04Sign in to DevyonQ

CanonQ is where a Mission lives, and the harness in DevyonQ reads and writes it for you. You sign the client in to DevyonQ once per computer, and every skill and every hook uses that sign-in.

Sign in, in a terminal of your own

Run the sign-in yourself, in a terminal outside the AI tool, from the folder Claude Code installed the plugin into. Your browser opens: sign in to DevyonQ, pick your tenant and approve. To skip the pick, add --tenant <tenant>, your tenant's id or your DevyonQ MCP address; https://app.devyonq.ai/choose-tenant lists your tenants with their ids to copy.

terminal · from the installed plugin directory
client/mc17 login
client/mc17 version        # Gateway and Tenant now name your DevyonQ

The client keeps what the sign-in answers in the credential store of your operating system, and refuses where none stands. No token goes into an environment variable or into a file a tool may read back, and no AI session can run the sign-in for you: the secret gate refuses a call that reaches it.

A session started on a computer that is not signed in yet says so at its start, with the exact command for that computer, and on Windows and macOS opens a window that runs the sign-in for you; Mission skills and mc17 commands wait until you are signed in. To keep that window from opening, create the empty file ~/.mc17/client/no-sign-in-window.

To sign this computer out, run mc17 logout the same way, in your own terminal. It removes the sign-in the client keeps; the key DevyonQ issued stays valid until it expires, or until you revoke "mc17, the client of devyonq-mc" under Connect AI agent in DevyonQ.

Who can run Missions

Any active person of the tenant who holds a DevyonQ seat may run Missions with this plugin. The tenant's reach covers a Mission collection only where the collection was made through the harness. A Mission made under a person's own CanonQ token stays on the old plugin.

The model of a decision point

A decision point's call spends your own OpenRouter key on the model you set on this computer, in a terminal of your own: client/mc17 config model <provider/model>. mc17 config model alone prints it, and --clear clears it. With no model set, the client spends nothing.

05Your first Mission

One command starts an interview. You answer as the person accountable for the work, and the skill writes a collection with four artifacts in it.

claude code
/mc-cre-mission-v17 Kaufland ERP

What the interview asks, and why

QuestionWhat it decides
Mission shapeStandard, Interface, Revision or Platform. Interface Missions have no architecture and no implementation plans.
AuthoritiesWho is accountable. If one person holds more than one role, say so, say what replaces the second pair of eyes, and say when that ends. Most first Missions have one person doing everything, and this is the field they usually fail on.
Work modesWhich artifacts are finished behind a gate, and which grow in the open under their owner's reading. The test: can this be finished without its authority reading it?
Delivery contextBranch policy, CI, release target, technology. Each takes N/A with a reason, which is the honest answer for a Mission that ships no code.
Does it run agent fleetsIf yes, the machinery is read from the harness rather than from you. Nobody is asked to recall a fingerprint.

What lands

A private collection named Mission Kaufland ERP holding MANIFEST-KAUFLAND-ERP-001, SPEC-KAUFLAND-ERP-001 and TP-KAUFLAND-ERP-001. It stays private until a person shares it in the app. Sharing is deliberately unavailable to agents.

06Verification, and the ledger

Creation writes a claim. Verification tests it, and writes what it found into a record nobody can edit afterwards.

claude code
/mc-vf-manifest-v17 Kaufland ERP

It checks 24 fields and a handful of cross-checks. The first time it runs, it creates the Mission's ledger: a JSON file that records every check ever run on this Mission. Records are only ever added to it. Nothing is edited or deleted, so the history of what was once wrong stays visible.

What the file format itself refuses

RuleWhat happens if you break it
The record number is assigned by the platformYour number is overwritten. Two agents appending at once cannot collide.
Verdict is one of PASS, FAIL, BLOCKED, NAThe write is refused and nothing is stored.
Evidence is command-and-output pairsA record with a claim and no command is refused.
An approval carries the authority's own wordsAn approval without them is refused at the write.

A refusal names the exact field. This is the whole reply to a bad append:

http 422 · nothing was written
Patch refused, nothing changed - schema violation at
/records/2/verdict: enum: must be equal to one of the
allowed values {"allowedValues":["PASS","FAIL","BLOCKED","NA"]}

Expect your first verification to fail

A brand new Manifest has fields only a person can fill in, so the first run almost always fails. Eleven test Missions were built while proving this out, and they nearly all failed on the same field:

FieldWhy it failsVerdict
5 AuthoritiesOne person holds several roles, and the compensating control and end condition are still empty.FAIL
2 SummaryNobody has written the two sentences a human reader acts on.FINDING
7 ModulesThe roster is provisional until an architecture is approved.WARNING

The writing check, and why it runs over what your agents wrote

Verification checks a Manifest. Everything else a Mission produces gets checked too, and the check is about how it reads. Documents written by agents drift toward long, dense and hard, and they drift fast. On one real Mission two implementation reports written a day apart came out at 14,000 and 31,000 characters, the second one far harder to get through. Nobody chose that. It just happened, because nothing was watching.

So there is a lint for governed writing, and one command runs it over anything already published:

terminal
client/mc17 lintdoc <asset id>

Title: IR-SAAS-IP-010-001
Violations: 30
  line 88   neg-foil-B   ...

It reads the document out of CanonQ by its id, so it works on anything that landed there. That is the point. A report written by one of your fleet agents, deep inside a run you were not watching, is read by the same command as a document you typed yourself. Who wrote it makes no difference.

Your verification runs this over every governed document the Move produced, and a hit is a finding against the document and its author. When we first ran it across a finished Mission it found 284 violations across 21 implementation reports, ranging from none to thirty-three in a single report. None of them had ever been read by anything.

You can point it at a local file too, with -f path.md, which is how you check a draft before it goes anywhere.

And you do not have to remember any of this. A second gate came with the plugin and it runs on the write itself:

QuestionAnswer
When it firesThe moment a governed document is about to be saved to CanonQ, before it lands.
What it coversManifests, specs, implementation reports, handoffs and the rest of the governed set. A scratch note passes untouched, because a gate that stops everything gets switched off by the first person it annoys.
What you seeThe save is refused and every offending line is named. Repair the text and save again.
Quoting someonePut the quotation in a fenced code block. The lint skips those, so you can reproduce anyone's words exactly.

It catches writes made through the tool and writes made by a script posting straight to the API, since both are the same act. If the gate itself breaks it lets your work through, so it can never become the reason you are stuck.

The Change Log, and why a document holds no history of its own text

Every governed document carries a ## Change Log table with four columns: the draft, the CanonQ version, what changed, and the ledger records. Its author adds one row for each write that changes what the document declares, before the plain-language pass, and the row names the version that write creates. CanonQ keeps every earlier text, so the log refers to an earlier version by its number and says nothing about what that text said.

terminal
client/mc17 versions <asset id>         # each version CanonQ holds, newest first, with its date
client/mc17 versions <asset id> --log   # fails a row that names a version CanonQ does not hold

In a document that carries the log, the writing lint refuses a sentence about the document's own earlier text under the rule history-prose, in the body and in the cells of the log. Delete the sentence and let the row refer to the version. A text with no Change Log, such as a hand-over, is refused nothing.

One rewrite per document, and a record of every write

A governed document goes through the plain-language rewrite once: over the whole document, before its first independent review. It goes through it again only when its reader says the word jargon, and then you send the change with mc17 amend --jargon. Every other change to what a document declares is sent with no rewrite. The amend runs the writing lint over the whole body, and for a Manifest, SPEC, ARCH, plan, Test Plan or Wave Plan it finds the record of that one rewrite in the ledger. A scaffold of an ARCH, a plan or the register of rulings, which mc17 create --scaffold sends with no rewrite, takes the pass at the first amend that moves its binding, and again at each such amend while a section still holds the template's placeholder.

terminal
client/mc17 plain --draft d.md --pass r.md --out p.json                # the proof of one pass
client/mc17 plain --draft r.md --pass r2.md --prior p.json --out p2.json  # a second pass, chained to the first
client/mc17 plain --exempt --draft d.md --manifest <id> --ledger <id> --out e.json  # a short body, below the threshold a Manifest row sets
client/mc17 create --title IP-X-001 --collection <id> --file r.md --plain p.json --manifest <id> --ledger <id>
client/mc17 amend <id> --edits e.json --class artifact --expect-binding moved --manifest <id> --ledger <id>

Each create, and each write that moves a binding, appends one record of the write to the ledger: the document, its version, its binding, what opened the send, and who ran the command. A person's own text goes out with --written-by, and only a name the Manifest's Authorities section lists passes. A figure the rewriter changed is printed as CHANGED and stops the send, because a rewriter has no authority to change a number. A write that changes a text removes the approvals of the old text in the same write, and the document's Approvals cell in the tracked table then reads none current, with the records kept.

The execution acceptance record

After each landing, one record accepts or refuses it: the person or session that merged writes it in a wave run by hand, and the session that launched the fleet writes it from the runner's return. mc17 append reads the record against its form before the send and refuses each fault by name. It needs --manifest and, where the landing is a commit, --repo; it accepts the run of the release checks at the pull request's tip where the tip's tree equals the merge's, or the integration stage's own run at the merged commit under --stage-run; it owes a line for each deviation of the report's Deviations section in a wave run by hand, or of the runner's return under --runner-return in a fleet wave; it owes the words of every role that approved an item a deviation narrows; it sends one record per report; and after the read-back it writes the record's number into the report's status line. mc17 append --draft writes the record's file with the lines a program reads already filled in, so a person types only what a person decides. A report rendered before the field moved into its status line predates the rule, and its record takes a form of its own; mc17 create refuses a report with no Deviations section from this release on.

A fix to a test after a stage can land under a narrow proof the authority rules, without both stages run again. His ruling opens NARROW PROOF <Wave Plan id> and names the commit the stage runs stand at, the fix commit that lands, the files the fix may change and the runs that prove the fix at the fix commit, each {host kind} {command} > {output file}, whose output opens with the line that shows its commit and its tree. Under --narrow <record>, the acceptance check and mc17 append --stage accept the landing at the fix commit only where the floor holds: the stage runs stand at an ancestor of the fix commit; the fix changes only test programs, the parts they load and the drill table, each named in the ruling; each test program a changed file belongs to ran whole and green at the fix commit on each host kind the Wave Plan names; and each drill row whose check text changed was proven again there, a hook row's text read with every file hooks/hooks.test.py runs. The integration record then stands at the fix commit and cites the stage runs, the ruling and each proof run.

The joins and the landing audit

Before a Mission closes, two joins and the landing audit read every landing. mc17 check <manifest> --ledger <id> --documents pairs each plan whose row reads Landed with its newest report and the latest execution acceptance record that names it, reads the report's field against that record, and then reads the Wave Plan the accepted record names: the plan fails where that Wave Plan is unruled, leaves it out, or has no passing integration record. mc17 landing --manifest <id> reads every ruled Wave Plan beside the tracked table and fails the merge of a plan of record that none of them names; a commit that names no plan is a release, which the audit lists with its parent count and its committer and fails nothing on. A landing made before the rule passes by its accepted record in the older form, a plan that changes only law texts passes by its amendment record, and a ledger that never took up the rule passes all three, each saying so in one line. None of them reads a date. The Move sweep records each failure, and the closure act refuses on each.

How the commands read a ledger, and its second version

The commands that read a ledger judge each record by what it already carries: its verdict, its place in the ledger and the first word of its text. mc17 ledger counts a defect record as closed by its own verdict PASS, or by a later record whose text opens RESOLVED {n} and names it, and prints each closed record with the rule that closed it. A RESOLVED record that stands before its defect closes nothing, and the command says so under the defect. mc17 dispatch --recite moves the dispatch of a review item to a later record that names the review, once, with the same disposition and note, and keeps the first record in the item as firstRecord. The evidence join reads repairs as a repair claim only on a record that opens RESOLVED or DEFECT; it reads a record that opens CORRECTION as a correction, and a record that opens with any other word as no claim, and fails on neither. mc17 append refuses repairs on a record that opens with any other word. A declared repair that repairs nothing stops failing the join where a later record that opens RESOLVED, of a verdict other than FAIL, declares its record in repairs and carries a REVIEW or VERIFICATION asset; mc17 evidence prints it as a note that names that record. Where an entry of a review's work order names a record from before the review record, a later ruling in an authority's own words whose first line reads exactly REDISPATCH {n}, naming the review record, and whose text holds a line Entry {id}: {disposition} dispatches the entry, which stays as written; mc17 reviewed and mc17 evidence print a note for each entry such a ruling dispatched and for each such ruling that dispatched nothing. mc17 reviewed and mc17 evidence also name a ruling whose first line opens REDISPATCH {n} and misses the exact form, and each line of such a ruling that opens Entry and misses the exact form. Under --recite, mc17 dispatch names the re-dispatching ruling where it refuses the re-citation of an entry whose dispatch names a record at or before the review record, because the review record names no REVIEW asset, the entry was re-cited once, or the disposition differs. A result manifest may mark a red case red-resolved:{n}, and mc17 accept then prints its criterion ok as accepted with resolved defect {n} where defect record {n} names the case and a later record that opens RESOLVED {n} carries the own words of the Business Owner or the Technical Owner; otherwise the case reads red, with the reason.

A ledger moves to version 2 by one command, mc17 ledger <ledger> --declare 2 --schema <asset id>. It binds the ledger to the asset ledger-hybrid-v2.schema, which holds every rule of version 1 and four fields more, and sets version2From to the next record's number, in one patch that tests what the command read. From that record on, every record names who wrote it down in recordedBy, and each passage of an authority's words names who spoke it in spokenBy, as BO {name} or TO {name}. mc17 append, the document hook and the evidence join apply the rule, and a record that carries recordedBy meets it on a ledger of either version. A later record that opens CORRECTION {n} and carries the missing fields clears record n's fault. A ledger whose two fields disagree is in a mixed state: mc17 append, mc17 ledger and mc17 evidence refuse it until the same command completes the declaration.

Both schema texts the harness holds, ledger-hybrid-v1.schema.json and ledger-hybrid-v2.schema.json, mark the records array with x-canonq-ledger: true and declare x-canonq-actor, an object, on a record and on a work-order entry. Once a CanonQ instance pins a ledger schema that carries both keywords, its QApp token grant reads them, and CanonQ writes x-canonq-actor itself; no command of this plugin adds it. A ledger whose bound asset holds either text refuses a record or an entry whose x-canonq-actor is no object, and reads every other record as before.

terminal
client/mc17 ledger <ledger>                                   # the version, the standing and the closed defect records
client/mc17 ledger <ledger> --declare 2 --schema <asset id>   # the move to version 2, in one tested patch
client/mc17 dispatch <ledger> --record <n> --item <id> --disposition applied --by <m> --recite

What the integration stage reads and runs

The integration stage takes each test setting from the Wave Plan's row first, then from the Manifest's row in force, then from the default, and prints where each value came from. The baseline reader takes its figures from the Test Plan entry of its case, and from AC-15 of the SPEC only where --spec names one. The stage leaves the acceptance case to the composition: mc17 append <ledger> --stage <dir> --manifest <id> --repo <path> runs the acceptance reader once, after the acceptance records exist, and the integration record reads PASS only where every landing of the wave has its record, written by the person who merged or the session that launched the fleet, citing a run that tested the merged code, with a report whose field read pending before it named the record. In a repository that holds no copy of the plugin, the stage runs the command the Wave Plan's Integration run: line names and records its exit code and its output. A release outside a wave gets its record from mc17 stage --release <sha>, which runs the ten release checks at the release's commit.

Where one reader of a finished run read red because an input was missing, and the commit and the tree have not moved since, the input is repaired and mc17 stage --rerun <run directory> --readers <name> runs that reader again over the run's own results. The suites, the drill and every other reader keep what the run wrote, and stage.json keeps its bytes. The rerun writes rerun.json beside it, and its outputs into a folder of its own under rerun/, so the record can show the first result beside the new one. It refuses a run of another Wave Plan, commit, host kind or tree, and names which, and it writes nothing then. The run directory stands outside the plugin's folder, where the run's files read as no edit of the plugin. mc17 append --stage reads each run with its rerun applied, takes the run's verdict again, and names the rerun on a line Rerun: {reader} at {time} on {host kind}; the check of an execution acceptance record reads each --stage-run directory the same way.

A ruled reading, and the programs that read it

When a criterion, a bar or a figure of a governed document stops the work, the authority whose approval the document needs may rule on the ledger how it reads for one wave, stage, plan or the rest of the Mission's work. A row of the Manifest's Operational Parameters table names that ruling record, so the row moves no binding and stales no approval. mc17 readings --manifest <id> --ledger <id> lists the rows, --row <n> writes one, and --check exits 1 while a row stands open or its reconciliation fails a test; the Move acceptance and the closure act run that check. A reading never touches nine of the ten release checks, the digest of the protected block or the measures of a judgment module. The drill alone may take one, and only where the Manifest's merge bar and its paragraph on collapsed authorities both carry the sentence A ruled reading may take the drill, mutations, and no other release check. Then mc17 gates, mc17 stage --release and mc17 stage run the other nine checks and report the drill as READ under ruling record {n}. A reading of a lens's bar reaches the fleet script, its lens briefs and the lock, a stage acceptance record may name a reading on its Reading: line, and mc17 accept reads a case state that names the record it rests on and the reading it was judged under.

The judgment module, its setting and its store

The command mc17 converge holds the twenty-five subcommands of the judgment module, and with no subcommand it lists them. mc17 converge probe makes one call on the model the setting wave.model.converge names, with a fixed policy and a fixed packet that holds no decision, and prints the model asked and the model that answered, the tokens, the price OpenRouter states, the time and the call state; it writes no file. Every new Wave Plan states the setting's row, none by default. A Wave Plan that lacks the row reads none, and mc17 wavecheck passes it with a NOTE: line. The key file is read at each call, and the transport to OpenRouter is refused in a test run.

A Mission's store stands outside the repository, on the one host where mc17 converge init --scope <SCOPE> made it, and every other subcommand refuses on another host. status prints one operation, disposition prints a stage's dispositions at a stage revision, and cancel cancels an operation that is not final, with a note of its cost so far, its unsettled charges and its deadline. key --init makes the key pair of the hidden cases once, and seal checks a set of cases, seals it and writes its sealing record, printing nothing of a case. A decision record goes to the ledger once: mc17 append --mark <operation id> looks for the record that mark names before it sends, and sends nothing where one stands.

Outside the fleet runner, mc17 converge evaluate --point <kind> asks the module once at a decision point of a wave run by hand: before a heavy run, which the hook hooks/lint-heavy.py refuses until a start entry of the store admits it under its key; before an agent start, over the prompt's file, which under wave.prompts template is the one line that names the agent's brief; at a review that blocks, over the lenses' results; at a red integration stage, whose last line names the command; and at the four loop points, from the runner's own facts. The command builds the packet from the point's own sources, asks the module once and writes the decision record. decide writes the deciding entry beside the module's record, the session's note or an authority's ruling in his own words, and ended reports an end the hook did not see. A stage start entry that no start used ends only with --stage-dir, which names the run's folder and marks the entry used by that run, or with --no-run, which the command reads against the ledger's integration records. Each running entry of a packet carries its wave, its plan and whether it belongs to the wave of the decision point, and a drill run counts once, its row workers and the shells that carry its command left out while its own process stands.

At every decision point the session shows the authority what mc17 converge offer prints, and at a stop still in the blind set what mc17 converge render prints, and adds no route of its own. The offer prints the sha256 of its lines as its last line, Digest. An authority's ruling through decide names what he was shown with --shown "offer <operation id> <digest>" or --shown "render <stop id> <digest>", and the command refuses a ruling with none, or with a digest other than the one it computes again, before any send; his blind decision at a stop of the set writes that line from the stop's SHOWN record. At a red stage, once the decision stands, decide, his blind decision and a call that applied the decision under a delegation print one line Run going : <table id> on <host>, keep or ..., stop for each run the packet lists still going. A fixed table sets each from the decision's action and whether the commit moved since the run: a targeted correction stops a run where the commit moved, a change of strategy stops it at either commit, and every other action keeps it. The session ends a run that reads stop.

The hook hooks/lint-heavy.py reads where a heavy run starts. On Windows it reads a Git Bash path in a cd, such as /c/Users/..., as the folder it names, and it writes a folder it cannot place to its journal where a wave run by hand stands on the host. It takes an agent start's folder from the newest agent entry of the store whose prompt digest matches the prompt, so the session starts each agent with the prompt as the file holds it. It reads a heavy run started over ssh in a remote checkout that mc17 wave lock --remote <ssh target>:<path> registers, by the cd the remote command holds, inside zsh -lc too, and judges it under the key of the target. It admits an admitted start only where a fresh reading of the host, the one mc17 converge host prints, matches the host's part of the packet and the wait condition holds, and it refuses a delegated start on a reading that fails or comes late, and a call of two delegated starts. At an agent start it takes only an entry made for the start's own prompt, open, admitted or held, and it refuses a start for whose prompt no entry stands with a refusal written for agent starts, which names the call owed. In a wave run by hand whose committed lock carries handPrompts, it refuses an agent start it places in the wave where the prompt is not the one line that names a brief, the brief is no start text the lock names, or its facts break their form, and it names the steps owed.

The blind test: once mc17 converge blind --open has started the set, the module's proposal at a stop of the set is sealed under the public key, the ledger carries its hash alone, and the command prints the stop's id and the hash. render writes the stop's facts under the program's labels with no action named, the Business Owner decides the stop in his own words, reveal opens each envelope of a stage once the stage has ended and checks the proposal against its hash, reading records his reading of each disagreement, and view shows the operator every decision, a sealed one hidden until its reveal; every read of a sealed proposal through a command goes into the store's read log. A ruling of the Business Owner in his own words that opens BLIND EXCLUDES <Wave Plan id> takes every point of that wave out of the set before it opens, so no proposal of the wave is sealed. A stop he takes out of the set by name after it was sealed is revealed as soon as his ruling stands, with reveal <stop id>, before its stage ends; a stop still in the set is refused.

The executor carries out a decision of the module where a delegation of the Business Owner covers it. A delegation is his ruling on the ledger, opening Delegation of in his own speaker line, that names the decision kinds, the stages and the Missions it covers, the early end, the ten reports it rests on with their versions, and the version record of the policy and the model; a later ruling that opens Revocation of delegation record {n} ends it. mc17 converge validate checks one decision against the delegations in force and the state as it stands now, and answers authorized, denied, stale or pending. mc17 converge apply then applies it once through the route its action takes at its point. At a heavy-run start and at a red stage the call of mc17 converge evaluate itself applies the decision at once where a delegation in force covers it. It writes each start entry once in its final state: admitted, for the start a step of the work order names on a host the proposal read idle, with the host's part of the packet and the wait condition, and held for every other start. At a red stage a targeted correction admits the one run its route names, the reader rerun at the run's own commit or the stage at the new tip, and a change of strategy, a challenge or a stop sends its decision request to the authority it names. The hook admits an admitted start only where mc17 converge host reads the host as the proposal found it and the wait condition holds, and a revocation appended ends the admitted starts of its delegation that no start used. mc17 converge offer prints what the authority would type and writes nothing, and mc17 converge recover settles each unsettled operation from the store alone after a restart. The lock reads the speaker line of every stage acceptance record and every targeted fix ruling: mc17 wave lock --resume --accept and --fix refuse a record with no line, or with a delegate's or an agent's, and admit the executor's line Speaker: executor under delegation record {n} only where that delegation stands.

Inside the fleet runner, a stage carries the field converge, which mc17 wave lock writes for a fleet plan with each member's delegations in force and mc17 wave script writes on each stage; --no-clerk writes the clerk off. At the four points of the review loop where a finding stands, the runner starts the clerk, a small agent that runs mc17 converge evaluate over the facts block and hands back its line Clerk :, and each call is an entry of convergence on the stage result and in the wave report. The runner waits for the clerk only where a delegation of the field names the early end at the point, and an authorized return there ends the stage early, with endedEarly on the result. After the wave the session writes the runner's return to a file and completes each call that names no decision record with mc17 converge evaluate --wave-report. Each recorded finding carries its id R{round}K{n}, and one targeted fix, taken by mc17 wave lock --resume --fix, follows a critical stop, a stop that still blocks or an early end, naming any finding the runner's return lists.

The policy file harness/converge/policy.md is the text the module sends the model with each packet. Its figure table, under the heading Figures, holds each figure the policy uses, with its source, its reason and its scope. mc17 converge policy --check <file> --ledger <id> refuses a policy where a figure lacks one of them, a number stands outside the table, or a sentence repeats a record kept from the module, and --adopt refuses a changed policy until its version holds a measure run of each of published, replay and judgment. version writes the version record that names the policy version and the model, once, and each run names that record. cases prints the prior cases of the Mission's decision and outcome records, each an analogy and no permission. run runs each case of a sealed set of the published, hidden or judgment set through the module's one call, in a run folder of the store, and writes a run record per case and a miss record per miss; a hidden run keeps its texts sealed until its records have landed, and --resume <run id> carries a stopped run on. load reads the host's load, the mean over three seconds, one reading after another, and writes no file; its highest reading under one heavy run gives the row of host-busy-load for the host's kind.

What a change of text owes

When a write changes what a document declares, the document owes a verification again, and every approval of its earlier text has lapsed. mc17 amend ends such a write with the line VERIFICATION OWED NOW: {skill}, naming the verifier skill of the document's class, and the skill that ran the amend runs that verifier before it reports. A write to a document of a class with no verifier, such as an Implementation Report, ends with NO VERIFIER: {class}.

terminal
client/mc17 check <manifest> --ledger <id> --documents               # every verification owed and every approval of an earlier text
client/mc17 check <manifest> --ledger <id> --approvals --doc <id>    # the approvals of one document alone
client/mc17 rework <manifest> --ledger <id> --record <n>            # the landed plans a verified SPEC change names go back to Rework
client/mc17 published <id> --ledger <id> --manifest <id>            # the version an authority reads, proven by its binding

The Move sweep runs the first form. It fails each document that owes a verification, naming the verifier, and each approval of a text that has since changed, naming the live-state write that takes that approval off the page. Each verifier skill runs the second form over its own document. Before an authority approves or rules, the skill runs mc17 published, and the approval or ruling record carries the line it prints last, Read: {asset id} version {n}, binding {hex}, verified at record {m}, so a later reader can check that the version on the page is the version the authority read.

A failed verification stamps nothing

It writes what it found into the ledger, with the command it ran for each check, and it leaves your Manifest untouched. Fill in the fields it named and run it again. Both runs stay in the ledger. That is deliberate: what was once wrong is part of the record.

07Running an agent fleet

A fleet is several AI agents working on one piece of work in sequence. One builds it. Two or three review it separately, without seeing each other's comments. Another fixes what they found, with a limit on how many rounds. A fresh reviewer who has seen none of that checks the result. A last one opens the pull request and merges it.

You do not write any of this, and you do not write the script either. You ask for the work in plain language and Claude Code writes it. This section is so you recognise what it produced and can read the message when a run is refused.

Why the guards are not yours to write

While this system was being built, four fleet runs went wrong in one day, all the same way. A merge check looked at how bad the findings were and forgot to read whether the reviewer had actually approved. A review loop was edited while it was running. One stage assumed the stage before it had finished, and never checked. The fourth was inside the code written to prevent the other three.

Every one of those was a safety check somebody meant to add and did not. So the checks are built into the thing you have to call anyway. You cannot forget them, because you never write them.

Who writes the script

Claude Code does. Not you. You describe the work in ordinary language, and the agent writes the workflow script, pastes the safety block into it, and runs it. In practice you will type something like:

claude code · what you actually type
Run a fleet to build the CommunicationHUB adapter.
Two review lenses: correctness, and what else it touches.
Land it as a pull request when the reviews clear.

That is the whole of your side. The paragraphs below are here so that when something goes wrong you can read the message and understand it.

What the agent produces, and why it looks odd

The script it writes starts with about 1,800 lines it did not compose. That is the safety block, pasted in whole. It looks like bloat and it is the point: a workflow script runs somewhere with no file access, so it cannot load the safety code from disk. It has to carry a copy.

Underneath the block sits the only authored part, usually a dozen lines. This is a one-stage fleet in full:

the part the agent writes · after the pasted block
const wave = openWave({
  waveId: 'erp-adapter',
  io: { agent, parallel, log },
  independentStages: 1,
  independenceBecause: 'first stage, nothing to build on',
  stages: [{
    name: 'adapter',
    dependsOn: null,
    build:  { prompt: 'Implement the CommunicationHUB adapter.' },
    lenses: [{ name: 'correctness', prompt: 'Judge it against the plan.' },
             { name: 'blast-radius', prompt: 'What else does this touch?' }],
    land:   { prompt: 'Open the pull request and land it.' },
  }],
})

Those dozen lines say what the work is. Everything that keeps it safe came with the pasted block, and you get all of it whether or not anyone thought to ask:

You getWhich means
One place decides whether it is safe to mergeIt reads whether the reviewer actually approved, not just how serious the findings sounded. A run once merged on "only minor issues" while a reviewer had said no.
The fix loop stopsFix, re-review, fix again runs a set number of times and then gives up and tells you. It cannot spin.
A stage is handed what actually mergedIf stage two builds on stage one, it receives stage one's real merge commit. It cannot build on something that never landed.
The fixer does not mark their own work as fixedA reviewer who has seen none of the earlier argument looks at the result fresh.
A failed merge stops the whole runThe stages after it do not start on the assumption that it worked.

Every one of those exists because it was once missing and something went wrong. That is why the block carries them for you, every time, on every script.

What runs the check, and when

The check is not something you remember to run. A small program sits between Claude Code and the thing that starts a fleet, and it runs every time. It is called a PreToolUse hook, and it came with the plugin.

QuestionAnswer
Who turns it onYou do, once, by installing the plugin in section 03. There is no second step. It then covers every Mission and every session on this machine.
How it gets registeredBy the file existing. The plugin ships hooks/hooks.json, and Claude Code reads it. You do not edit any settings file.
Where it runsOn your own machine, as a local process. It reads the script and runs the lint. It never reaches the network and never touches CanonQ.
When it firesThe moment a fleet is about to start, before anything runs. A clean script gets silence and starts normally. A bad one is stopped and named.

Two behaviours are worth knowing because they will look strange otherwise. When the script is clean, the hook says nothing at all, so a silent run is the check passing. And if the hook itself breaks, it lets a script through that carries no safety block. A gate that blocks everything gets switched off by the first person it annoys, and then nothing is checked at all. A fleet script, one that carries the safety block, is stopped when the hook cannot read it, and the message names the cause, because a fleet that nobody checked against its ruled plan should not run.

The reason it exists is the plainest argument in this whole guide. The rule that fleets must use the safety code was written down, and a command existed to check it. Nobody ran the command. All thirty-one fleet scripts written while building this system broke the rule, including the ones that were checking the methodology. A check that waits to be remembered is not a check.

When you see it refused

If the agent writes a script that reaches for an AI agent outside the pasted block, the run is stopped before anything happens and you see a message like this:

the run was denied · nothing executed
G4-unsanctioned-script  this script reaches the runtime agent
2 time(s) outside a verified sanctioned block, and the script
carries no verified sanctioned block at all.

Read it as: this script was going to run AI agents without the safety code around them. Nothing ran, nothing was written, nothing is broken. Tell the agent to paste the block and declare the wave properly, and it will.

The other message you might see says fence-tampered. That means the pasted block was edited. Even one character breaks it, on purpose: an edited copy is no longer the code that was tested, so every safety rule inside it stops counting at once.

If you ever do want to write one

Two commands, and the second one is worth knowing regardless because it is what the hook runs for you.

terminal
client/mc17 block --print > wave.js   # the block to paste
client/mc17 lint wave.js              # check it yourself

Violations: 0
Clean. Every reach for an agent stands inside a verified sanctioned block.

A worked example ships with the plugin at harness/examples/sanctioned-wave.js. It is the script mc17 wave script writes from the fixture Wave Plan, so it shows the form every fleet script takes: export const meta first, three declaration lines naming the ruled plan, its prompts and every setting in force, and return await main() last.

Each lens of a fleet Wave Plan states its bar, the defects it blocks on, in one line beside its brief. mc17 wavecheck refuses a lens with none, and the script carries each bar beside its lens, where the prompt digest reads it. In the opening review a finding blocks only where it falls under the bar; in a re-review only where it raises a blocking finding of the round before again, or falls under the bar in a part the fix report names. Every other finding is recorded for the authority, and the Implementation Report lists it. A recorded finding graded critical stops the stage. A stage that stopped in its review loop returns the head an authority may accept by a ruling record, or fix by one targeted fix, under the same ruled Wave Plan. A build that opened no pull request stops its stage before any lens runs, and a lander that states it used no bypass claims none.

The lock on the branch

A ruled Wave Plan is locked onto its branch by mc17 wave lock, which commits the file .mc17/wave.json there. When a fleet is about to start, the hook reads that committed lock and runs the check against it. You can run the same check yourself:

terminal
git show mission/x:.mc17/wave.json > lock.json
client/mc17 lint wave.js --lock lock.json   # the launch reading

Four things follow from the lock:

  • A script whose plan, settings or prompts differ from what the lock records is stopped and named. So is a script that runs stages on a branch with no committed lock.
  • After a stop, mc17 wave lock --resume takes the remainder of the wave into the lock, with the authority's acceptance of a stopped stage's head, or one targeted fix after a critical stop, a stop that still blocks or an early end, for findings the runner's return lists, and mc17 wave script --resume writes the remainder script from the same ruled plan. The check then admits that script's seed and holds it to the entry: its order, its prompts, its acceptance or its targeted fix. An acceptance or a targeted fix that no entry carries is stopped in every script.
  • The lock guards the branch it names, whatever that branch is called, and every branch whose name starts with mission/.
  • A commit that edits the committed lock is refused, whatever token it carries, with one exception: the commit of a resume entry, which mc17 wave lock --resume makes under the wave token and which the override never passes. Otherwise a lock changes only through mc17 wave unlock and mc17 wave lock, and each leaves a commit of its own.
  • A merge commit on a locked branch needs the wave's token, as a commit does, through the pre-merge-commit hook beside the pre-commit hook.

If a repository installed the hooks with an earlier release, run mc17 wave hooks there again. It replaces the plugin's own older hook and adds the merge hook, and a repository takes no remainder into its lock until it has.

Where this check does not reach

It watches one door. Fleets started the way section 07 describes go past it. A fleet started by handing work straight to a single agent uses a different door, and that door has no check on it. A script that reaches an agent by some route the check has never seen will also pass while doing whatever it likes.

One more thing to expect: if you install the plugin while Claude Code is already running, restart it. Whether a running session picks up a new hook by itself is untested, and a restart settles it.

Really fixing that means the thing that runs your script hands you a safe agent and no other, and nobody has built that yet. Saying so is better than letting you assume you are covered.

09When it refuses

Most refusals name the thing to fix. These are the ones whose message points somewhere other than the cause.

What you seeWhat it means
the client holds no sign-in. Run mc17 login in a terminal of your own. This computer has not signed the client in to DevyonQ yet. Run client/mc17 login yourself, in a terminal outside the AI tool, and pick your tenant in the browser, or add --tenant <tenant>. Nothing is guessed on purpose: the client never picks a DevyonQ or a tenant for you.
A hash that does not match anything You hashed the wrong bytes. The REST route returns the body inside a JSON envelope, so hashing the whole reply gives a perfectly normal-looking wrong answer. Use mc17 hash, which unwraps it and self-checks.
the bound schema is unusable A platform fault, not a fault in your record. No repair to the record clears it. Stop, report the binding, and never rebind a ledger to a different schema to get past it.
Verification says a pinned document moved The law changed under your Mission. That is the pin working. Re-pinning is a decision by the Business Owner and Technical Owner, recorded as a Manifest change, and never something a skill does quietly.
The lint denies a script you believe is fine Read the line it names. If it says fence-tampered, the pasted block was edited, and every guard it defined is now outside the verified region. Re-paste with mc17 block --print.

The habits worth taking from this

  • Run the subject's implementation, never a copy of it. A recipe transcribed into a document drifts from the code it describes, and then the check certifies the drift.
  • Watch every check fail before trusting it. Break the thing, see the red, restore, see the green.
  • A finding that reaches nobody has not been produced. Publish it in the act that produces it, not in a step afterwards that you might drop.
  • A rough first draft is part of the job, not a failure. Some documents cannot be finished until the person accountable has read them and reacted. Publish those early and let them grow, instead of polishing in private.

10Your own settings

You can give every Claude Code session that works for you the same standing orders. They live in four CanonQ documents that belong to you, and each session reads all four whole before it acts.

The four sit together in one restricted collection your account owns, titled MC Settings {Full Name} and filed under the category DevyonQ Settings, on the CanonQ instance that keeps your settings. Your initials close each title.

The four documents

  • ORDERS-{XX}: the way you want sessions to work with you;
  • MANDATE-{XX}: what a session may decide or do for you, and what waits for your word;
  • SETUP-{XX}: your machines, your accounts and the hazards each of them carries;
  • MISSIONS-{XX}: a row for each Mission you work in, kept up to date by the plugin's skills and commands as a Mission starts, hands over and closes.

Making them

Run mc-cre-settings-v17 {Full Name} in a session of your own. Once you say so, it creates the collection and the four documents from the templates the harness holds. Where a collection of yours stands already, it fills in only what is missing. It names each near miss, a collection of yours that fails part of the test, with what to change in the app, and makes no new collection while one stands.

The command underneath

mc17 settings finds your collection by the login your credentials carry, and every change the plugin makes to your four documents goes through it. mc17 settings --check holds your MISSIONS table against every Manifest that names you, prints each difference with the line that settles it, and changes nothing.

What belongs in them, and how a rule gets in

One rule decides what your settings hold: ORDERS, MANDATE and SETUP hold only what is about the person and holds in every Mission; a project's or a Mission's facts, such as its paths, repositories, names, figures and record numbers, stay in that Mission's own documents, which the MISSIONS table links.

A session puts each new entry in front of you whole, as it will land, before it is written, and the command writes it once you confirm that text. An entry that carries none of your own words first passes an adversarial check, made by an agent working in a context of its own. The command turns away an entry whose wording around your words names a project's fact, such as a path, a repository, an id, a record number, a URL or a host name.

To have your settings reviewed, ask in your own words, such as "review my settings", or run mc-adv-settings-v17 review. Every closure act runs one for the person who closes the Mission. A panel of independent agents does the reading, and your session publishes the review in your own collection and hands you its link.

How a session receives them

As each session starts, the plugin's session-start hook hands it your four documents whole, in labelled parts, together with the machine, the plugin version, the host, your login and your account's name. Each line the hook adds on its own opens with [MC settings]. An agent that a session starts receives nothing from the hook: it gets what the session's brief gives it.

Until MANDATE is read

Where a session starts and the hook could not hand it your MANDATE whole, that session sends nothing to production or to other people, and gives no approval in your name, until it has read that document. It holds back in the same way while another editor's version of MANDATE waits for your confirmation, which your session records with mc17 settings --confirm-version.

Sharing them

Share the collection in the app, and then a colleague with ordinary rights can edit its documents. CanonQ keeps every version of each one, and a colleague's change reaches every one of your sessions at its next start, which tells you about it.

Each machine you work on

Once the hook is installed and finds your credentials, a machine needs no pointer to the documents in ~/.claude/CLAUDE.md, and no other setting. Keep this one line in that file, for any session in which no plugin hook runs:

~/.claude/CLAUDE.md
Where no line opening [MC settings] stands in this session's context, the session reads the person's settings with mc17 settings before its first act, or, where the plugin is not loaded, through its CanonQ connector from the one restricted MC Settings collection the person names, and, until it has read MANDATE, sends nothing to production or to other people and gives no approval in the person's name, unless the person's word in the chat names that one act.
